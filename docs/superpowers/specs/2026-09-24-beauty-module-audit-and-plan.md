# Beauty module: code audit, architecture, and development plan

Date: 2026-09-24. Status: proposal for review; no product implementation is authorized by this document. The current VoltaMarcada source is the authority for platform, tenancy, licensing, and cash behavior. SalonSync is a reference for beauty workflows, not a migration source.

## 1. Outcome and scope

Add a Beauty product to the existing four-project solution while preserving the recurrence workflow. Its first sellable flow is: configure professional and service, show computed availability, book an appointment, perform the service, record a single cash obligation/payment; or sell a package, pay for it once, book and consume its service-specific credits, and retain an auditable history. Public booking selects a professional or any eligible professional. A company can eventually enable either or both products. No SalonSync project, database, UI, or financial subsystem is copied into VoltaMarcada.

This is an architecture and delivery plan only. The proposals below must be reviewed before product code or migrations are created.

## 3. SalonSync audit and reuse matrix

The documents `MVP.txt`, `FluxoAgenda.txt`, and `RegrasDeNegocioAgendamento.txt` describe a barber/beauty flow, employee/service selection, consecutive slot use, active packages, and cancellation. The code differs from parts of those documents. The classifications below are about adoption in VoltaMarcada: **A** reuse essentially as-is, **B** preserve the rule and reimplement, **C** adapt a subset, **D** discard.

| SalonSync part and purpose | Actual behavior, quality, dependencies | Decision |
| --- | --- | --- |
| `Employee`, `Service` | Employee has one daily start/end and lunch interval, optional commission, owner `UserId`; service has duration/price. Simple but lacks weekly variations, leave, service eligibility, and protected state. | **C**: retain domain inputs, model separate Beauty entities and weekly availability. |
| `Appointment`, `AppointmentGroup`, `AppointmentHandler.OpenByEmployeeIdAsync` | Generates and persists many `Free` appointment rows for each day/time; booked services may occupy a group of rows. Depends on mutable EF entities and a fixed slot size. | **D** for stored free rows and group-as-booking; **B** for complete-duration occupancy. Use one appointment interval and computed candidates. |
| `AppointmentHandler.GetAvailablesHoursByEmployeeIdAsync` | Rounds duration to a slot count, seeks consecutive `Free` rows and suggests a future date. The grouping loop skips overlapping candidate starts. Some future-date queries lack owner filtering. | **B**: preserve full-duration/contiguous availability and future alternatives; reimplement deterministic interval logic with tenant scope. |
| `Package`, `PackageService` | Package price plus per-service session counts; `TotalSessions` sums them. No immutable sale snapshot. | **C**: retain per-service entitlements, add validity and sale snapshots. |
| `ClientPackage` | One aggregate `RemainingSessions`; creating a new active purchase deactivates an existing active package. Uses wall clock and mutable setters. Cannot reliably distinguish entitlement per service or preserve overlapping purchases. | **D** for the counter/forced deactivation; **B** for validity and remaining-credit rule. |
| `ClientPackageAppointment` | Link to a package purchase and one appointment row, with limited history; creation writes separately after booking. | **B**: keep traceable purchase-to-booking relationship, create a durable credit movement with state and idempotency. |

| Cancellation (`AppointmentHandler.CancelAsync`) | Stores a history snapshot, then resets booked rows to `Free`. Credit restoration is commented out. Written rule is not implemented behavior. |
| Public schedule endpoint | Resolves a company code, overwrites `request.UserId`, and calls the same creation handler anonymously. Client-provided entity IDs and the separate booking call still need full ownership/eligibility checks; no database overlap constraint was found in this flow. | **C** retain company-scoped public URL and service/professional selection; **D** direct endpoint adaptation. |
| `Transaction`/`PaymentService`/cost centers | Separate financial model with `EntityType`/`EntityId`; UI initiates payment separately from package or appointment lifecycle. | **D** as a cash subsystem; VoltaMarcada cash remains authoritative. No tenant filter appears in its SQL. | **D** for code. Optional commission percentage may be recorded later; defer payout accounting until separate acceptance criteria exist. |

## 4. Divergences requiring product decisions

| Divergence | Options | Recommendation |
| --- | --- | --- |
| Package credit timing: SalonSync document says decrement on booking; code decrements at completion from the UI. | Reserve on booking and consume on completion; or consume immediately and later refund. | Reserve one service-specific credit atomically at booking, consume on completion or configurable no-show/late cancellation, release on eligible cancellation. This prevents overbooking credits while preserving an audit trail. |
| Cancellation deadline: document uses only “before/after start”; request suggests a configurable allowed period. | Fixed before-start rule or per-company cutoff. | A company-level Beauty cutoff in hours, default 24, with explicit initiator/reason and owner override. Freeze the policy version/decision on each cancellation. Confirm the commercial default before rollout. |
| Public customer registration: VoltaMarcada requires valid document and address; salons typically ask name/phone. | Keep existing mandatory data on public Beauty booking; or allow a separate provisional customer profile and later enrichment. | Use a Beauty booking contact/provisional profile for public checkout; link to an existing `Customer` only after safe identity confirmation. Do not silently relax shared `Customer` invariants or merge people by phone alone. A follow-up decision should set the exact public identity fields. |
| Public booking confirmation: recurrence creates a request/preference; proposed Beauty flow creates a booking. | Reuse request model or create a real Beauty appointment. | Create an actual Beauty appointment after final availability check and database constraint; show confirmation. Keep recurrence semantics unchanged. |
| Package validity and overlapping purchases: SalonSync deactivates prior package. | Single active package or multiple independent purchases. | Support multiple purchases, immutable sale snapshots, each with independent expiration and FIFO selection among eligible paid/active credits. |
| Package refunds: current cash handles positive charges and deletion of installments, but no explicit refund/outflow workflow. | No refund in MVP or targeted reversal support. | Package cancellation/credit release is distinct from sale refund. For monetary refund, add a small auditable cash reversal capability before enabling sale refunds; never represent it as deleting original income. |
| Same person as recurrence and Beauty professional | Share `Professional`/calendar or separate entities. | Separate Beauty professional and calendar. If one person later serves both products, add an explicit cross-product resource link and shared conflict enforcement; until then do not promise combined availability. |

## 5. Proposed architecture and boundaries

Keep `VoltaMarcada.slnx` and its four projects. In `Domain`, add `Beauty` entities/value objects under a feature namespace. In `Application`, add Beauty commands/queries/use cases and narrow persistence interfaces. In `Infrastructure`, add EF configurations and implementations in Beauty folders, within the existing `AppDbContext`. In `Web`, add Beauty pages/components/endpoints using the existing composition root, theme, and authorization system. Keep the recurrence classes in place; no broad move to a new Core project.

Shared platform: Company, Identity/CompanyUser, current company, license access, common Customer when a verified record exists, cash charge/installments, file/notification infrastructure, layout/theme. Beauty-owned: professional, service, weekly hours/breaks/blocks, appointment, booking policy, package catalog, package purchase, entitlements and credit movements, and Beauty customer notes/history. A Beauty use case may call a small application cash-port operation. The cash module must not reference Razor components or infer revenue from an appointment.

Module entitlements: initially create a company/module entitlement with `ModuleCode` (`Recurrence`, `Beauty`), status and effective dates; backfill `Recurrence` for current companies so existing access stays available. An authorization service checks membership, license mode, and entitlement for internal Beauty operations; public Beauty URLs check enabled/active company and Beauty publication policy. Existing `CompanyLicense` continues to govern platform access. Future product plans/limits can be attached to module subscriptions instead of replacing license lifecycle now. Billing amount for Beauty must be explicit and separate from `LicenseBillingOptions.MonthlyPrice`; do not change existing renewal price as a side effect.

## 6. Domain model and relational design

Names below are proposals, consistent with existing English PascalCase database objects. Every tenant-owned table has `CompanyId`, an FK to `Companies`, and composite `(CompanyId, Id)` alternate key where another tenant table references it. Child FKs include `CompanyId` to prevent cross-company links.

| Aggregate/table | Responsibility and key relationships | Index/constraint |
| --- | --- | --- |
| `CompanyModuleEntitlements` | Company, module code, status, effective dates. | Unique `(CompanyId, ModuleCode)`; backfill existing companies for Recurrence. |
| `BeautyProfessionals` | Identity/display, active flag, optional `CompanyUserId`, optional commission setting (configuration only). | `(CompanyId, Name)`; unique optional linked company user; tenant composite FK. |
| `BeautyServices` | Name, description, positive duration, price, active/public flags. | `(CompanyId, IsActive, Name)` based on list/public queries. |
| `BeautyProfessionalServices` | Eligibility join. | Unique `(CompanyId, ProfessionalId, ServiceId)` with both tenant composite FKs. |
| `BeautyWorkingHours` / `BeautyScheduleBlocks` | Weekly local intervals and dated absence/break overrides. Breaks can be stored as separate weekly intervals or explicit subtractions. | Unique/prohibit overlapping hours for professional/day in application plus persistence checks; indexed blocks by company/professional/start. |
| `BeautyAppointments` | One actual occupied `[StartAtUtc, EndAtUtc)` interval, professional, service, contact/customer, origin, status, price snapshot, timestamps. | Composite FKs; `(CompanyId, ProfessionalId, StartAtUtc)` index; positive interval check; partial GiST exclusion on company, professional, UTC range for occupied statuses. |
| `BeautyAppointmentEvents` | Cancellation/reschedule/no-show/completion record, actor, reason, old/new interval, policy decision. | `(CompanyId, AppointmentId, CreatedAtUtc)`; immutable history. |
| `BeautyPackageDefinitions` / `BeautyPackageDefinitionItems` | Sellable catalog and per-service credit counts, price, validity days, active flag. | Unique item `(CompanyId, DefinitionId, ServiceId)`; positive counts/price/validity checks. |
| `BeautyPackagePurchases` / `BeautyPackagePurchaseItems` | Customer-owned sale, purchased price and immutable service/count snapshots, start/end date and status. | `(CompanyId, CustomerId, ExpiresOn)`; tenant composite FKs; edits to catalog do not change sold entitlements. |
| `BeautyPackageCreditMovements` | Immutable reserve, release, consume, expire, and owner-adjust events per purchase item and appointment. | Unique event key for retry safety; index `(CompanyId, PurchaseItemId, CreatedAtUtc)` and `(CompanyId, AppointmentId)`; balance is computed or transactionally maintained with concurrency check. |
| `BeautyCashLinks` | Exactly one nullable `PackagePurchaseId` or `AppointmentId` points to one existing `WorkOrderCharge`, saved in the same database transaction. | Check exactly one source is set; filtered unique indexes on `(CompanyId, PackagePurchaseId)` and `(CompanyId, AppointmentId)` plus unique `(CompanyId, ChargeId)`; composite FKs to both Beauty source tables and charge. |
| `BeautyBookingContacts` (if public identity decision accepts provisional contact) | Minimal public contact and verified linkage to shared `Customer`. | Scoped by company; no automatic phone-based merge. Define retention/privacy policy before launch. |

Use `Guid` IDs, UTC instants, `DateOnly` for local validity, and `TimeOnly` for weekly local hours. Company timezone is not currently an explicit `Company` property, so a timezone setting and conversion policy are a prerequisite for correct multi-zone Beauty scheduling. Validate daylight saving gaps/ambiguities on slot generation. Keep physical deletion away from appointments, purchases, credit events, and paid charges; deactivate catalog entries instead. The exact EF migration table list follows the accepted public-contact and billing decisions.

## 7. Use cases and behavior

Configuration: `CreateBeautyProfessional`, `UpdateBeautyProfessional`, `ChangeBeautyProfessionalStatus`, `AssignBeautyProfessionalServices`, `SaveBeautyWorkingHours`, `CreateBeautyScheduleBlock`, `CreateBeautyService`, `UpdateBeautyService`, `ChangeBeautyServiceStatus`, `ConfigureBeautyBookingPolicy`.

Scheduling: `GetBeautyAvailableSlots`, `CreateBeautyAppointment`, `RescheduleBeautyAppointment`, `CancelBeautyAppointment`, `StartBeautyAppointment`, `CompleteBeautyAppointment`, `MarkBeautyAppointmentNoShow`, `GetBeautyCalendar`, `GetBeautyCustomerHistory`. Public: `GetPublicBeautyCatalog`, `GetPublicBeautySlots`, `SubmitPublicBeautyBooking`, `GetPublicBeautyBooking`, `CancelPublicBeautyBooking` using a secure, scoped token where customer self-service is permitted.

Packages: `CreateBeautyPackageDefinition`, `UpdateBeautyPackageDefinition`, `SellBeautyPackage`, `RecordBeautyPackagePayment`, `GetBeautyPackageBalance`, `ReserveBeautyPackageCredit`, `ReleaseBeautyPackageCredit`, `ConsumeBeautyPackageCredit`, `ExpireBeautyPackageCredits`, `AdjustBeautyPackageCredit` (owner only, reason required). An appointment with package payment mode must bind to one eligible purchase item for the selected service; no “any session” counter.

Recommended appointment states: `Scheduled`, `Confirmed` (only if a distinct confirmation action is product-relevant), `InProgress`, `Completed`, `Cancelled`, `NoShow`. Keep payment status and credit state separate from appointment status. Omit `Confirmed` initially if it has no actual user action. Cancelled appointments remain records, not free rows. Reschedule updates an appointment and appends a history event; package reservation remains attached when service is unchanged and new date is valid, otherwise release/re-reserve atomically.

## 8. Cash integration and package accounting

Treat `WorkOrderChargeInstallment` as the Cash screen's authoritative money row. For a standalone Beauty service, completion creates a charge for the service price snapshot, pending until collected, and a `BeautyCashLink` to that appointment; retries must find the existing link. For a package sale, create the purchase, credit grants, one charge for its sold price, and the link in one transaction. If the package is allowed before collection, reserve/use permissions must explicitly reflect pending status; recommended MVP rule is that credits become usable only after the sale charge is fully paid. A successful payment changes the existing installment; it does not create another charge. Booking, completion, cancellation, release, and expiry of prepaid sessions produce **zero** additional cash income. A standalone service never inherits a package discount or credit implicitly.

The current `CreateManualCashEntryUseCase` is not the integration API: it auto-confirms and has no source identifier. Add a narrow cash operation for source-linked pending charges plus a read projection that displays the Beauty source on the existing Cash screen. Keep the work-order path and existing cash totals unchanged. Put uniqueness on the Beauty source link and save the source/charge/link together so a retry cannot double-post. A refund requires an auditable reversal/negative movement capability in the shared cash model and a package status change in the same transaction. A credit adjustment alone must never masquerade as a refund.

## 9. Availability, public booking, and concurrency

For the chosen local date, service, and optional professional: load active eligible professionals within the company; intersect their weekly intervals with date-specific working exceptions; subtract breaks, leave, blocks, and occupied Beauty appointments; enumerate candidate starts at the configured Beauty interval; retain a candidate only if the complete service interval fits one available segment and meets lead-time/public horizon rules. Convert local intervals to UTC with the company timezone. Return chronological starts and eligible professionals; for “any professional,” return a time once with an eligible set, then choose one by an explicit fair/deterministic rule at final write. Do not persist free slots. Cancelled bookings cease to occupy time; in-progress bookings still occupy it. The recurrence company's public request interval does not control Beauty real-time slots.

At final internal/public creation and rescheduling, validate tenant, entitlement, professional-service eligibility, active records, policy, package credit, and full interval again on the server. Run write within a transaction. A PostgreSQL `btree_gist` partial exclusion constraint on `BeautyAppointments` prevents overlapping occupied ranges for the same company/professional under concurrent requests. Catch its specific violation and return “slot no longer available.” Schedule-block writes also need conflict checks against existing bookings, with a clear reject/reassignment workflow; the appointment exclusion alone does not cover block overlaps. For purchase credits, lock the purchase item row or use optimistic concurrency plus a database check so two bookings cannot reserve the last credit. The transaction must include reservation and appointment creation.

## 10. Tenant security and authorization

Resolve internal `CompanyId` only from `ICurrentCompany`; never accept it from a form or route as authority. Filter every Beauty read/write by company and ID. Composite tenant FKs prevent a Beauty appointment from referencing another company's professional, service, customer, or purchase. Public routes resolve a company by slug, check Beauty entitlement/publication, and query only its public-active services/professionals. Public cancellation or booking context uses random non-guessable tokens, expiry, rate limiting, minimal response data, and server-side validation; internal IDs are not authorization tokens. Avoid a global query filter as a substitute for repository review because the current code relies on explicit scoping.

Initial matrix: Owner configures catalog, professionals, policy, packages, manual credit overrides, and Cash; Owner and authorized Employee can view/manage Beauty appointments and perform service; public visitor may read published catalog/slots and submit booking. Existing Employee role alone does not authorize cash, package-price edits, or overrides. If employee booking permissions need granularity, add Beauty permissions tied to `CompanyUser`, not Identity platform roles. Module and license checks run in use cases/endpoints as well as navigation; hiding a menu item is not authorization.

## 11. UI

Add a Beauty section to the existing shell, visible only with entitlement: calendar/day view, appointments list/details, professionals list/registration, services list/registration, working hours/blocks, packages list/editor, package sales and balances, customer Beauty history, and settings. Add public Beauty catalog, professional/date/time picker, contact form, confirmation and safe cancellation flow under a route distinct from recurrence's public company page (for example `/beauty/{companySlug}`). Extend the existing Cash display with source labels/links and pending/paid status; do not add a second cash page. Reuse MudBlazor, shared page headers and input components, theme, loading/error/empty states, and mobile patterns. No SalonSync UI is copied.

## 12. Migration and rollout sequence

1. Baseline: capture current migration/snapshot and run existing integration tests against a test PostgreSQL instance. Back up a representative database for migration rehearsal. No production schema action in this stage.
2. Add module entitlement table and backfill `Recurrence`; leave existing license and routing behavior unchanged. Make Beauty disabled by default.
3. Add timezone setting and Beauty professional/service/schedule tables with tenant keys and checks. Seed no fake availability rows.
4. Add Beauty appointments/events and the GiST exclusion constraint; verify migration up/down on a copy and confirm open-status predicate.
5. Add package definitions/purchases/items/credit movements and credit concurrency protection. Snapshot sold catalog values.
6. Add `BeautyCashLinks` plus the minimal shared charge factory/projection/reversal changes needed by the accepted payment policy. Existing work-order rows remain valid; do not rewrite their IDs or amounts.
7. Enable internal Beauty UI behind entitlement, then public booking with rate limits and monitored rollout. Use incremental migrations with reversible additive schema changes wherever possible.

For every migration, inspect generated SQL and model snapshot, test old data readability, verify unique/index creation on representative volume, and ensure existing recurrence routes and Cash totals remain stable. Avoid mixing a recurrence table rename with a Beauty migration.

## 14. Main risks and open decisions

1. **Cash is currently work-order-shaped.** A naive manual entry loses source and auto-confirms. The source-linked pending-charge adapter and idempotent link must precede package sale rollout.
2. **Package rule conflict.** Written SalonSync rules and executable behavior differ. Reserve-on-booking/consume-on-completion is recommended, but the cancellation cutoff, no-show, owner override, refund and unpaid-sale policy need product acceptance.
3. **Customer friction.** Shared `Customer` requires document and address. A provisional public contact avoids a silent domain rewrite, but its identity/merge and retention policy need approval.
4. **Timezone correctness.** Existing company model has no explicit timezone. Introduce it before real-availability public booking, including DST tests.
5. **Cross-product capacity.** Separate calendars permit the same human to be booked in both modules if manually represented twice. MVP must either prohibit dual assignment operationally or add explicit shared-resource linking and constraints before marketing combined calendars.
6. **Entitlement and billing.** Existing single monthly license is not a multi-plan catalog. Backfill protects Recurrence; Beauty pricing and limits are a separate commercial decision.
7. **Schedule block concurrency.** Appointment exclusion prevents booking collisions, not simultaneous vacation/block insertion; block creation needs transaction-aware conflict handling.
8. **Historical integrity.** Avoid mutable package balances with no ledger, deletion of paid entries, and catalog edits that change previously sold terms.

Recommended next decision checkpoint: approve the architecture and choose public Beauty contact requirements, package cutoff/no-show/refund policy, unpaid-package access, Beauty price/entitlement rollout, and whether a person may work in both calendars. Then turn the accepted slices into task-level implementation plans. Product code and migrations begin only after that review.
